# Week 3 — Processes, Signals, and the Services that Never Sleep

> Date range: 2026-09-25 ~ 2026-09-29 ・ Phase: Phase 1 / Week 3 ・ Status: ✅ done

## Focus
Understand what a process is (a running instance of a program), how to observe the system (`ps` / `top`), how to control it (`kill` + signals), and how systemd keeps services alive — the same mental model you will need later for GPU task scheduling and multi-model concurrency.

## Learned
- **Process = a running program.** The program on disk is a static file; a process is a living instance with its own PID (the ID card), memory, and state. One program can run as many processes.
- **`ps aux` (BSD style) vs `ps -ef` (System V style):** Linux supports both Unix lineages. `a` = all users, `u` = user-friendly format (USER/CPU/MEM), `x` = include daemons **without a terminal** (that's what makes postgres/docker visible).
- **The process family tree:** PID 1 (`/sbin/init`, systemd) is the ancestor of everything; orphaned processes get adopted by it. WSL adds its own glue processes: `/init`, `plan9` (file sharing behind `/mnt/c`), `wsl-pro-service`.
- **Reading `top`:**
  - Row 1: `up` time + `load average` (1/5/15 min) — compare against **CPU core count** (`nproc`), not 1.0.
  - Tasks line: sleeping processes are normal; **0 zombie** is healthy.
  - `%Cpu(s)`: `us` user / `sy` kernel / `id` idle.
  - **VIRT vs RES:** VIRT = address space *reserved* (numpy/pandas reserve tens of GB, harmless); RES = *actual* physical memory. Judge memory by RES.
  - ⚠️ **Terminal-width trap:** in a narrow window, top **truncates row 1** — `up` and `load average` disappear. Fix: widen the window, or use batch mode `top -b -n 1` (full-width, one-shot, script-friendly → `top -b -n 1 > snapshot.txt`).
- **Signals (the Unix way to talk to processes):**
  - `SIGTERM (15)` = a **message**: the process may clean up (save files, flush, release locks) or even refuse. Output: `Terminated`.
  - `SIGKILL (9)` = an **action**: the kernel destroys it instantly, nothing can refuse or clean up. Output: `Killed`.
  - Order of battle: **15 first, wait, then 9.** Graceful = "the process participated in its own exit".
  - `kill -l` lists the whole signal family (2 = Ctrl+C, 9, 15, 20 = Ctrl+Z…).
- **`&`, `$!`, and the traps:**
  - `sleep 300 &` runs in the background and returns the prompt immediately; `$!` = PID of the **most recent** background job.
  - `$!` gets **polluted** if any other background command runs in between — always confirm with `ps aux | grep [s]leep` (the `[s]` trick keeps grep from matching its own command line).
  - `kill` on an already-dead PID → `No such process`: that's *expected*, not an error — it proves the process is gone.
- **systemd (the services manager):** the first process, which starts and supervises all services.
  - `systemctl list-units --type=service`: UNIT / LOAD / ACTIVE / SUB / DESCRIPTION. **`exited` is normal** for one-shot tasks (set console font, seed snapd) — they ran and finished.
  - `systemctl status cron`: `Loaded: enabled` = start at boot; `Active: running since …` = current state; `Main PID` connects back to the PID you saw in `ps`; the journal at the bottom is the service's unified log (`journalctl -u cron` for all of it).
  - Four switches: `enable/disable` (permanent: at boot?) vs `start/stop` (right now) — independent of each other.
- **AI tie-in:** a process sleeping vs running (STAT S ↔ R) is the same idea as a GPU task waiting for its turn — the OS schedules processes, the GPU driver schedules kernels.

## Hands-on
```bash
ps aux | head -20          # family tree incl. daemons (TTY = ?)
ps -ef | head -5           # System V style: PPID column
ps aux | grep [s]leep      # the [s] trick: no self-match

top                        # live view; P/M sort by CPU/mem; q to quit
top -b -n 1                # full-width one-shot snapshot (script-friendly)

sleep 300 &                # background job → [1] 1857
echo $!                    # last background PID
kill 1857                  # SIGTERM → Terminated
sleep 300 &                # again…
kill -9 <PID>              # SIGKILL → Killed

systemctl list-units --type=service | head -10
systemctl status cron      # Loaded / Active / Main PID / journal
systemctl stop cron ; systemctl start cron   # dead → alive, live demo
```

## Errors & fixes
| Error | What I tried | What actually fixed it |
|---|---|---|
| `top` didn't show the `up … load average` line | Wondered where it went | Terminal too narrow → row 1 truncated. Widen window or use `top -b -n 1` (batch mode ignores window width) |
| Typed `echo &!` instead of `echo $!` | — | `&` ran an extra background `echo`, so `$!` pointed at *that* PID (1917), not sleep (1857). Lesson: `$!` = most recent bg job; confirm real PIDs with `ps` |
| `kill 1917` → `No such process` | — | Expected: that echo had already finished. Killing a dead PID is harmless and confirms it's gone |
| `ps aux \| grep sleep` matched grep itself | — | `grep [s]leep` — the bracket pattern can't match its own literal `[s]leep` command line |

## Meta: what I learned about learning
- **Signals are a vocabulary, not magic:** "Terminated" vs "Killed" is the signature of which conversation the kernel had with the process (a message vs an action).
- **Observability first, action second:** `ps`/`top`/`systemctl status` are read-only eyes; only act (`kill`, `stop`) when you can name the PID you verified yourself.
- **The same process model recurs everywhere:** OS processes → GPU kernels → containers. Learn it once here, reuse it in AI infra later.

## English corner
- `daemon` — 守护进程（常驻后台的服务进程）
- `graceful exit` — 优雅退出（进程参与了自己的退出过程）
- `signal` / `terminate` / `kill` — 信号 / 终止 / 杀死
- `load average` — 平均负载（和 CPU 核数比才有意义）
- `virtual vs resident memory` — 虚拟内存 vs 常驻内存（VIRT 是订座，RES 是坐下）
- `truncate` — 截断（窄终端把 top 第一行裁掉了）
